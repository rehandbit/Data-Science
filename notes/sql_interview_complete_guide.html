Basics
Q1What is SQL and what are DDL, DML, DCL, TCL?
▼
DDL — Data Definition Language
Defines structure
CREATE, ALTER, DROP, TRUNCATE. Changes the schema/structure of tables.
DML — Data Manipulation Language
Manipulates data
SELECT, INSERT, UPDATE, DELETE. Works with the data inside tables.
DCL — Data Control Language
Controls access
GRANT, REVOKE. Manages user permissions on database objects.
TCL — Transaction Control Language
Manages transactions
COMMIT, ROLLBACK, SAVEPOINT. Controls transaction flow.
Say this
"SQL is a language for managing and querying relational databases. It has four sublanguages — DDL for defining structure like creating and altering tables, DML for working with data through select, insert, update and delete, DCL for managing permissions, and TCL for controlling transactions with commit and rollback."
Q2What is the order of execution in a SQL query?
▼

SQL does not execute in the order you write it. This is one of the most tested SQL fundamentals.

1.FROM / JOIN — get the data and combine tables
2.WHERE — filter rows
3.GROUP BY — group the filtered rows
4.HAVING — filter the groups
5.SELECT — choose which columns to return
6.DISTINCT — remove duplicates
7.ORDER BY — sort the results
8.LIMIT / OFFSET — restrict number of rows returned
Say this
"SQL doesn't execute in the written order. It starts with FROM to get the data, then WHERE to filter rows, then GROUP BY to group them, then HAVING to filter groups, then SELECT to pick columns, then ORDER BY to sort, and finally LIMIT. This is why you can't use a SELECT alias in a WHERE clause — WHERE runs before SELECT."
Classic trap
You cannot reference a SELECT alias in WHERE. e.g. SELECT salary * 1.1 AS new_salary WHERE new_salary > 50000 — this fails because WHERE runs before SELECT. Use a subquery or CTE instead.
Q3What are the different types of keys in SQL?
▼
Primary keyUniquely identifies each row. Cannot be NULL. Only one per table. e.g. user_id.
Foreign keyLinks one table to the primary key of another. Enforces referential integrity. Can be NULL.
Unique keyEnsures all values in a column are unique. Unlike primary key, allows one NULL and can have multiple per table.
Composite keyPrimary key made of two or more columns together. Used when no single column is unique enough on its own.
Candidate keyAny column that could be the primary key — unique and not null. The chosen one becomes the primary key, others are alternate keys.
Say this
"Primary key uniquely identifies every row and cannot be null — there is exactly one per table. Foreign key creates a link between tables and enforces referential integrity. Unique key also enforces uniqueness but allows one null and multiple unique keys per table. A composite key uses two or more columns together as the primary key."
Q4What is the difference between WHERE and HAVING?
▼
WHERE
Filters rows
Runs BEFORE GROUP BY. Filters individual rows. Cannot use aggregate functions like SUM, COUNT.
HAVING
Filters groups
Runs AFTER GROUP BY. Filters groups created by GROUP BY. Can use aggregate functions.
SELECT department, COUNT(*) AS emp_count FROM employees WHERE salary > 30000 -- filters rows first GROUP BY department HAVING COUNT(*) > 5 -- then filters groups
Say this
"WHERE filters rows before grouping — it cannot use aggregate functions. HAVING filters groups after GROUP BY — it can use aggregates like COUNT or SUM. Simple rule: if you need to filter on an aggregate result, use HAVING. For everything else, use WHERE."
Common mistake
Writing HAVING without GROUP BY. HAVING is almost always paired with GROUP BY. Without it, the whole table is treated as one group.
Q5What is the difference between DELETE, TRUNCATE, and DROP?
▼
DELETE
Removes rows
DML. Removes specific rows using WHERE. Can be rolled back. Slow — logs each row. Table structure stays.
TRUNCATE
Clears all rows
DDL. Removes ALL rows. Cannot use WHERE. Faster than DELETE. Usually cannot be rolled back. Resets auto-increment.
DROP
Removes table
DDL. Removes the entire table including structure, data, and indexes. Cannot be rolled back. Gone completely.
Say this
"DELETE removes specific rows using a WHERE clause and can be rolled back — it's DML. TRUNCATE removes all rows at once, is faster because it doesn't log individual rows, but cannot be rolled back in most databases — it's DDL. DROP removes the entire table including its structure permanently. Think of it as: DELETE = erase some content, TRUNCATE = erase all content, DROP = destroy the book entirely."
Q6What is the difference between UNION and UNION ALL?
▼
UNION
Removes duplicates
Combines results of two queries and removes duplicate rows. Slower due to deduplication step.
UNION ALL
Keeps duplicates
Combines results and keeps ALL rows including duplicates. Faster. Use when duplicates are acceptable or impossible.
Say this
"Both combine results from two SELECT statements — the columns and data types must match. UNION removes duplicate rows but is slower because it performs a deduplication step. UNION ALL keeps all rows including duplicates and is faster. I always use UNION ALL by default unless I specifically need deduplication, because it avoids unnecessary performance cost."
Watch out
Both queries in a UNION must have the same number of columns and compatible data types. Column names in the result come from the first SELECT.
Joins
Q7What are the types of JOINs? Explain each.
▼
INNER JOINReturns only rows where there is a match in BOTH tables. Most common. Unmatched rows from either table are excluded.
LEFT JOINReturns ALL rows from the left table, and matched rows from the right. Unmatched right rows become NULL. Most used after INNER.
RIGHT JOINReturns ALL rows from the right table, matched rows from the left. Unmatched left rows become NULL. Rarely used — can always rewrite as LEFT JOIN.
FULL OUTER JOINReturns ALL rows from both tables. NULLs fill in where no match exists. Use to find all records with or without a match.
CROSS JOINReturns cartesian product — every row in table A combined with every row in table B. No ON clause. n × m rows. Rarely used intentionally.
SELF JOINA table joined to itself using aliases. Used for hierarchical data — e.g. finding employee and their manager from the same table.
-- SELF JOIN example: employee and their manager SELECT e.name AS employee, m.name AS manager FROM employees e JOIN employees m ON e.manager_id = m.employee_id
Say this
"INNER JOIN returns rows with a match in both tables. LEFT JOIN returns all rows from the left table regardless of a match — unmatched right columns are NULL. FULL OUTER JOIN returns everything from both tables with NULLs where no match exists. CROSS JOIN produces every combination of rows from both tables. SELF JOIN joins a table to itself — useful for hierarchical structures like an employee-manager relationship in one table."
Q8What is the difference between INNER JOIN and LEFT JOIN?
▼

This is the most asked join question — know a concrete example.

-- Customers table: 100 customers -- Orders table: 70 customers have orders SELECT c.name, o.order_id FROM customers c INNER JOIN orders o ON c.id = o.customer_id -- Returns 70 rows (only matched customers) SELECT c.name, o.order_id FROM customers c LEFT JOIN orders o ON c.id = o.customer_id -- Returns 100 rows (all customers, NULL for those with no order)
Say this
"INNER JOIN only returns customers who have placed an order — 70 rows. LEFT JOIN returns all 100 customers — those without an order get a NULL in the order columns. Use LEFT JOIN when you want to keep all records from the main table regardless of whether a match exists. This is how you find customers who have never ordered — add WHERE o.order_id IS NULL."
Finding non-matching rows
LEFT JOIN + WHERE right_table.id IS NULL is the classic way to find rows in table A that have NO match in table B — e.g. customers who never ordered, users who never logged in.
Aggregate functions and GROUP BY
Q9What are aggregate functions?
▼
COUNT(*)Counts all rows including NULLs. COUNT(column) counts only non-NULL values.
SUM(col)Sum of all non-NULL values in a column.
AVG(col)Average of non-NULL values. Ignores NULLs — can be misleading.
MAX(col)Highest value. Works on numbers, dates, and strings.
MIN(col)Lowest value.
SELECT department, COUNT(*) AS total, AVG(salary) AS avg_salary, MAX(salary) AS highest FROM employees GROUP BY department HAVING COUNT(*) > 3
Say this
"Aggregate functions compute a single result from multiple rows. COUNT(*) counts all rows including NULLs — COUNT(column) counts only non-null values in that column, which is an important distinction. AVG ignores NULLs, which means if 10 out of 100 values are NULL, it averages the remaining 90 — the denominator is 90, not 100."
COUNT(*) vs COUNT(column)
COUNT(*) = 100 rows total. COUNT(salary) = 90 if 10 salaries are NULL. This difference matters and interviewers test it.
Subqueries and CTEs
Q10What is a subquery? What are its types?
▼

A query nested inside another query.

ScalarReturns exactly one value. Used in SELECT or WHERE. e.g. WHERE salary > (SELECT AVG(salary) FROM employees)
RowReturns one row with multiple columns. Used with row comparison operators.
Table / derivedReturns multiple rows and columns. Used in FROM clause as a temporary table.
CorrelatedReferences the outer query — re-runs for every row of the outer query. Powerful but slow.
-- Scalar subquery: employees earning above average SELECT name, salary FROM employees WHERE salary > (SELECT AVG(salary) FROM employees) -- Correlated subquery: employees who earn more than their department avg SELECT name, salary, department FROM employees e1 WHERE salary > ( SELECT AVG(salary) FROM employees e2 WHERE e2.department = e1.department -- references outer query )
Say this
"A subquery is a SELECT nested inside another SQL statement. Scalar subqueries return one value and can go in WHERE or SELECT. Table subqueries return a full result set and sit in the FROM clause as a derived table. Correlated subqueries reference the outer query and re-execute for every outer row — they're flexible but can be slow on large datasets, where a JOIN or CTE is usually more efficient."
Q11What is a CTE and how is it different from a subquery?
▼

CTE = Common Table Expression. A named temporary result set defined before the main query using WITH.

-- CTE version WITH dept_avg AS ( SELECT department, AVG(salary) AS avg_sal FROM employees GROUP BY department ) SELECT e.name, e.salary, d.avg_sal FROM employees e JOIN dept_avg d ON e.department = d.department WHERE e.salary > d.avg_sal
CTE
Named, readable
Named and reusable within the same query. Much more readable. Can be recursive. Defined with WITH at the top.
Subquery
Inline, nested
Anonymous and inline. Harder to read when nested deeply. Cannot be reused in the same query. No WITH clause.
Say this
"A CTE uses the WITH keyword to define a named temporary result set before the main query. Compared to subqueries, CTEs are much more readable — especially for complex logic — and can be referenced multiple times in the same query. I prefer CTEs over subqueries for anything more than a simple one-liner because they make the logic easy to follow and debug step by step."
Q12What is a recursive CTE?
▼

A CTE that references itself — used for hierarchical data like org charts, file systems, or category trees.

-- Find all employees under a manager (hierarchy) WITH RECURSIVE org_chart AS ( SELECT id, name, manager_id, 1 AS level FROM employees WHERE manager_id IS NULL -- anchor: top of tree UNION ALL SELECT e.id, e.name, e.manager_id, oc.level + 1 FROM employees e JOIN org_chart oc ON e.manager_id = oc.id -- recursive part ) SELECT * FROM org_chart ORDER BY level
Say this
"A recursive CTE references itself to traverse hierarchical data. It has two parts — an anchor member that starts the recursion (like the root of a tree), and a recursive member that joins back to the CTE itself to go one level deeper each iteration. It's the standard way to query tree structures like org charts, product categories, or bill of materials in SQL."
Window functions
Q13What are window functions? How are they different from GROUP BY?
▼

Window functions perform calculations across a set of rows related to the current row — without collapsing rows like GROUP BY does.

GROUP BY
Collapses rows
Reduces multiple rows into one per group. You lose access to individual rows after grouping.
Window function
Keeps all rows
Calculates across a window of rows but every original row stays in the result. The OVER() clause defines the window.
-- Show each employee, their salary, AND their department average SELECT name, department, salary, AVG(salary) OVER (PARTITION BY department) AS dept_avg, salary - AVG(salary) OVER (PARTITION BY department) AS diff_from_avg FROM employees
Say this
"Window functions perform calculations across related rows without collapsing the result like GROUP BY does. The OVER() clause defines the window — PARTITION BY divides rows into groups like GROUP BY, and ORDER BY within OVER determines the order for running calculations. The key advantage is that every original row remains in the output, so you can compare each row to its group's aggregate in one query."
Q14ROW_NUMBER vs RANK vs DENSE_RANK — what is the difference?
▼
-- Salaries: 100, 90, 90, 80 -- ROW_NUMBER: 1, 2, 3, 4 (always unique, no ties) -- RANK: 1, 2, 2, 4 (ties get same rank, next rank skips) -- DENSE_RANK: 1, 2, 2, 3 (ties get same rank, next rank does NOT skip)
ROW_NUMBERAlways unique sequential number. Ties broken arbitrarily. Use when you need exactly one row per rank.
RANKTies get the same number. Next rank skips (gaps). Like real sports rankings — two 2nd places means no 3rd.
DENSE_RANKTies get same number. Next rank does NOT skip. No gaps. Use when you want consecutive ranks.
Say this
"All three assign a rank to rows. ROW_NUMBER always gives a unique sequential number — ties are broken arbitrarily. RANK gives tied rows the same number but then skips — two second-place ties means no third place. DENSE_RANK also gives ties the same number but never skips ranks. I use ROW_NUMBER when I need unique rows like deduplication, DENSE_RANK when I want clean consecutive rankings."
Most common use case
ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date DESC) = 1 — this gets the most recent order per customer. Classic deduplication pattern.
Q15What are LAG and LEAD functions?
▼

Access values from previous or next rows without a self join.

SELECT month, revenue, LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue, LEAD(revenue) OVER (ORDER BY month) AS next_month_revenue, revenue - LAG(revenue) OVER (ORDER BY month) AS month_over_month_change FROM monthly_sales
LAG(col, n)Value from n rows BEFORE the current row. Default n=1. Returns NULL for first row.
LEAD(col, n)Value from n rows AFTER the current row. Default n=1. Returns NULL for last row.
Say this
"LAG and LEAD access values from previous or following rows in the result set. LAG looks back, LEAD looks forward. They're perfect for calculating period-over-period changes — like month-over-month revenue growth — without needing a self join. The first row's LAG is NULL since there's no previous row."
Q16What is PARTITION BY and how is it different from GROUP BY?
▼
PARTITION BY
Window function only
Divides rows into groups for window function calculation. All original rows are kept in output. Used inside OVER().
GROUP BY
Collapses to one row
Reduces all rows in a group to a single summary row. Individual row data is gone after grouping.
Say this
"PARTITION BY is used inside window functions with OVER() to divide rows into groups for the calculation — but unlike GROUP BY, all rows remain visible in the result. GROUP BY collapses each group into one row. If I want the average salary per department AND see each individual employee's row, I use PARTITION BY. If I only want one summary row per department, I use GROUP BY."
NULL handling
Q17How does SQL handle NULL values?
▼

NULL means unknown or missing — not zero, not empty string. NULL behaves differently from any other value.

NULL = NULLFALSE. NULL is not equal to NULL. Use IS NULL or IS NOT NULL — never = NULL.
ArithmeticAny operation with NULL returns NULL. 5 + NULL = NULL.
AggregatesCOUNT(*) includes NULLs. COUNT(col), SUM, AVG all IGNORE NULLs.
COALESCEReturns first non-NULL value. COALESCE(col, 0) replaces NULL with 0.
NULLIFReturns NULL if two values are equal. NULLIF(col, 0) returns NULL when col = 0 — avoids divide by zero.
SELECT COALESCE(salary, 0) AS salary -- NULL becomes 0 SELECT NULLIF(sales, 0) -- 0 becomes NULL (avoid div/0) SELECT 100.0 / NULLIF(total, 0) AS rate -- safe division
Say this
"NULL means unknown in SQL — not zero or empty. The critical thing is NULL does not equal NULL, so you must use IS NULL instead of = NULL. Any arithmetic with NULL returns NULL. COALESCE is my go-to for replacing NULLs with a default value, and NULLIF is useful for safe division — converting zeros to NULL prevents divide-by-zero errors."
Classic trap
WHERE col != 5 does NOT return rows where col is NULL. NULL comparisons always return UNKNOWN, which is treated as FALSE. You must add OR col IS NULL explicitly.
Indexes
Q18What is an index? When should you use it?
▼

An index is a data structure that speeds up data retrieval — like an index in a book that lets you jump to the right page.

Without indexFull table scan — database reads every row. O(n). Slow on large tables.
With indexB-tree lookup — jumps directly to matching rows. O(log n). Much faster for reads.
Use index onColumns used in WHERE, JOIN, ORDER BY, GROUP BY. High-cardinality columns (many unique values). Primary and foreign keys.
Don't indexLow-cardinality columns like boolean flags. Small tables. Columns rarely used in queries.
Pros
Dramatically faster SELECT and JOIN queries. Essential for large tables.
Cons
Slows down INSERT, UPDATE, DELETE — index must be updated. Takes extra storage space.
Say this
"An index is a data structure — usually a B-tree — that allows the database to find rows without scanning the entire table. It's like a book index: instead of reading every page, you jump to the right location. Indexes speed up reads but slow down writes because the index must be maintained on every insert, update, or delete. I add indexes on columns frequently used in WHERE, JOIN, and ORDER BY clauses, and on foreign keys."
Q19What are the types of indexes?
▼
ClusteredPhysically reorders the table rows to match the index. Only ONE per table. Primary key is usually clustered by default.
Non-clusteredSeparate structure with pointers back to the actual rows. Multiple allowed per table. Most common type.
CompositeIndex on multiple columns. Column order matters — most selective column first. Useful for multi-column WHERE/JOIN.
Unique indexEnforces uniqueness on a column. Created automatically by UNIQUE constraint.
Full-textFor searching within text fields. Used with MATCH...AGAINST or CONTAINS. Standard B-tree doesn't work for text search.
Say this
"Clustered indexes physically sort the table data — there can only be one per table and it's typically the primary key. Non-clustered indexes are separate structures that point back to the table rows — you can have many per table. Composite indexes cover multiple columns and are powerful for queries that filter on those columns together — but column order matters, with the most selective column first."
Normalisation
Q20What is normalisation? Explain 1NF, 2NF, 3NF.
▼

Normalisation is the process of organising a database to reduce redundancy and improve data integrity.

1NFEach cell has only ONE value (no lists). Each row is unique (has a primary key). No repeating column groups. e.g. phone1, phone2, phone3 columns → separate phone table.
2NFMust be 1NF PLUS every non-key column depends on the WHOLE primary key — not just part of it. Only relevant when composite primary key exists.
3NFMust be 2NF PLUS no transitive dependencies — non-key columns should depend only on the primary key, not on other non-key columns. e.g. storing employee's zip code AND city — city depends on zip, not on employee_id.
Say this
"Normalisation reduces data redundancy and prevents anomalies. First Normal Form requires atomic values — no lists in cells — and unique rows. Second Normal Form requires every non-key column to depend on the entire primary key, not just part of it. Third Normal Form removes transitive dependencies — non-key columns must depend only on the primary key, not on other non-key columns. In practice, 3NF is the standard target for most OLTP databases."
Denormalisation
Sometimes we intentionally denormalise — combine tables or add redundancy — for read performance in analytical/reporting databases (data warehouses). It's a deliberate trade-off: faster reads, more storage, harder to update.
ACID properties
Q21What are ACID properties?
▼
A — Atomicity
All or nothing
A transaction either completes fully or not at all. If any step fails, the whole transaction rolls back. No partial updates.
C — Consistency
Valid state always
A transaction takes the database from one valid state to another. All rules and constraints are respected.
I — Isolation
Transactions independent
Concurrent transactions don't interfere with each other. Each transaction sees a consistent snapshot.
D — Durability
Committed = permanent
Once committed, changes are permanent — even if the system crashes immediately after.
Say this
"ACID stands for Atomicity, Consistency, Isolation, Durability. Atomicity means a transaction is all-or-nothing — a bank transfer either debits one account and credits another completely, or neither happens. Consistency means the database always moves from one valid state to another. Isolation means concurrent transactions don't see each other's uncommitted changes. Durability means committed data survives system crashes — it's written to disk permanently."
Classic example
Bank transfer: debit £100 from account A, credit £100 to account B. Atomicity ensures you can't debit without crediting — if the credit fails, the debit is rolled back automatically.
Views, stored procedures and performance
Q22What is a view? What is the difference between a view and a table?
▼

A view is a saved SELECT query — it looks like a table but stores no data itself.

CREATE VIEW active_customers AS SELECT id, name, email FROM customers WHERE status = 'active' -- Now use it like a table SELECT * FROM active_customers WHERE city = 'London'
ViewVirtual table. Stores only the SQL query, not data. Data is always current — fetched fresh on each query.
Materialised viewStores the actual query result as a physical snapshot. Must be refreshed. Faster to query, but data may be stale.
TablePhysically stores data. You own the data. INSERT/UPDATE/DELETE work directly on it.
Say this
"A view is a virtual table based on a saved SQL query — it stores the query definition, not the data. Every time you query a view, it runs the underlying SQL fresh. Views simplify complex queries, enforce security by exposing only certain columns, and create a consistent interface. A materialised view stores the actual result on disk for performance — but the data can be stale until refreshed."
Q23What is a stored procedure vs a function?
▼
Stored procedure
Executes logic
Can perform DML (INSERT/UPDATE/DELETE). Returns zero or many results. Called with EXEC/CALL. Can have side effects.
Function
Returns a value
Must return a single value or table. Can be used inside SELECT. No side effects (in pure functions). Cannot do DML in most DBs.
Say this
"Stored procedures are precompiled blocks of SQL logic stored on the database server — they can contain DML statements, conditionals, and loops, and are called with EXEC or CALL. Functions must return a value and can be embedded in SQL expressions — like SELECT my_function(col) FROM table. The key practical difference: functions can be used inside a query, stored procedures cannot."
Query optimisation
Q24How do you optimise a slow SQL query?
▼
1. EXPLAIN planRun EXPLAIN or EXPLAIN ANALYZE first. Shows which operations are slow — full table scans are the red flag.
2. Add indexesIndex columns in WHERE, JOIN, ORDER BY. Dramatically reduces scan time on large tables.
3. Avoid SELECT *Only fetch columns you need. Reduces I/O and network overhead.
4. Filter earlyPut the most restrictive WHERE conditions first. Reduce rows as early as possible in the pipeline.
5. Avoid functions in WHEREWHERE YEAR(date_col) = 2024 prevents index use. Use WHERE date_col BETWEEN '2024-01-01' AND '2024-12-31' instead.
6. Replace correlated subqueriesRewrite as JOINs or CTEs — correlated subqueries re-run for every row.
7. Use LIMITDon't return millions of rows when you only need a sample.
Say this
"My first step is always EXPLAIN ANALYZE to see the query execution plan and identify bottlenecks — full table scans on large tables are the main culprit. Then I check whether the right indexes exist on JOIN and WHERE columns. I also avoid wrapping indexed columns in functions, which breaks index usage. And I replace correlated subqueries with JOINs or CTEs since correlated subqueries re-execute for every row."
Common interview problems
Q25Find the second highest salary.
▼
-- Method 1: DENSE_RANK (best approach) SELECT salary FROM ( SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk FROM employees ) ranked WHERE rnk = 2 -- Method 2: Subquery SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees) -- Method 3: OFFSET (simple but fragile) SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1
Say this
"I prefer the DENSE_RANK approach because it handles ties correctly and generalises to Nth highest salary just by changing the rank number. The subquery method works for second highest but gets messy for third or fourth. I'd avoid OFFSET in production as it can behave unexpectedly with ties."
Q26Find duplicate rows in a table.
▼
-- Find duplicates: rows where same email appears more than once SELECT email, COUNT(*) AS count FROM users GROUP BY email HAVING COUNT(*) > 1 -- Delete duplicates, keep one (using ROW_NUMBER) WITH duplicates AS ( SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn FROM users ) DELETE FROM users WHERE id IN ( SELECT id FROM duplicates WHERE rn > 1 )
Say this
"To find duplicates I GROUP BY the columns that define uniqueness and use HAVING COUNT greater than 1. To remove duplicates while keeping one copy, I use ROW_NUMBER() OVER PARTITION BY the duplicate columns — rows with row number greater than 1 are the duplicates to delete."
Q27Find employees who earn more than their manager.
▼
-- Self join: join employees table to itself SELECT e.name AS employee, e.salary AS emp_salary, m.name AS manager, m.salary AS mgr_salary FROM employees e JOIN employees m ON e.manager_id = m.id WHERE e.salary > m.salary
Say this
"This is a classic self join — joining the employees table to itself using aliases. One instance represents the employee, the other represents their manager linked by manager_id. Then I just filter where the employee's salary is greater than their manager's salary."
Q28Running total / cumulative sum.
▼
-- Running total of sales by date SELECT date, amount, SUM(amount) OVER (ORDER BY date) AS running_total, SUM(amount) OVER (PARTITION BY month ORDER BY date) AS monthly_running_total FROM sales
Say this
"A running total uses SUM as a window function with ORDER BY inside OVER(). Without PARTITION BY it's a cumulative sum across the whole dataset. Adding PARTITION BY month resets the running total for each month. This is much cleaner than a self join approach."
Q29What is the difference between IN, EXISTS, and ANY?
▼
INChecks if a value matches any value in a list or subquery result. Evaluates subquery fully first. Good for small lists.
EXISTSChecks if a subquery returns ANY rows. Stops as soon as one match is found. Faster than IN for large subqueries.
ANY / ALLCompares a value to any (or all) values in a subquery. salary > ANY(subquery) means greater than at least one value.
-- IN: matches from a list SELECT * FROM orders WHERE customer_id IN (1, 2, 3) -- EXISTS: faster for large subqueries SELECT * FROM customers c WHERE EXISTS ( SELECT 1 FROM orders o WHERE o.customer_id = c.id )
Say this
"IN evaluates the full subquery result and checks membership — it's simple but loads all results into memory. EXISTS stops as soon as it finds the first match, making it faster for large datasets. As a rule of thumb, use IN for small fixed lists, and EXISTS for correlated subqueries on large tables."
Q30What is the difference between a clustered and non-clustered index?
▼
Clustered index
Physical sort order
The table rows are physically stored in the index order. Only ONE per table. Very fast for range queries. Usually the primary key.
Non-clustered index
Separate structure
A separate lookup structure pointing back to table rows. Many allowed per table. Slightly slower than clustered but still far faster than full scan.
Say this
"A clustered index physically reorders how the rows are stored on disk — the data IS the index. Because there's only one physical storage order, a table can only have one clustered index. A non-clustered index is a separate structure with pointers back to the actual rows — like a book's index pointing to page numbers. You can have many non-clustered indexes. Range queries are fastest with clustered indexes because the data is physically adjacent on disk."
